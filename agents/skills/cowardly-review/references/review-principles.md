# レビューで繰り返し確認する観点

この一覧は、蓄積済みのレビュー知見から複数のリポジトリで使える観点を抜き出したもの。すべてを毎回確認するのではなく、差分に関係する項目だけ使う。

## データとAPI契約

- 入力から検証、変換、永続化、読み戻しまで追う。APIが成功値として返すフィールドが、実際にDBへ保存されるとは限らない。
- 省略、`null`、空文字、ゼロ値、既定値を区別する。後方互換性とエラー時の動作も確認する。
- 更新処理が列を明示する場合、新しいフィールドが書き込み対象に含まれているか確認する。

## 分岐と影響範囲

- 共有ヘルパーやシグネチャを変更したら、すべての公開入口と呼び出し側を追う。追加した分岐だけでなく、従来経路も維持されるか確認する。
- 同じ識別子集合、同じ境界条件、同じロック対象を前後の処理が使うか確認する。集計・削除・再試行・並行実行では特にデータ整合性を見る。
- 変更の直接的なコード影響と、実行環境・本番負荷・費用への推定を分ける。計測されていない実行時効果を確定事項として扱わない。

## テストの証拠力

- テストが変更の目的に沿った意味のある出力を検証しているか確認する。件数、部分文字列、コピーした設定値だけの検証は、誤実装を通す場合がある。
- テストデータが実際の本番設定・スキーマ・呼び出し経路に接続しているか確認する。
- 正常系に加えて、境界値、欠落値、結合対象の欠落、複数回通る経路、既存経路など、変更が壊し得るケースを選ぶ。
- 「テストがある」ことを正しさの証明にしない。疑わしい挙動があれば、既存テストの結果や小さな再現実験で確かめる。

## セキュリティと外部境界

- 権限、認証主体、信頼できない入力、秘密情報の読み取りから送信まで、成立する経路を具体的につなぐ。
- ログのマスキングや説明文だけを安全境界とみなさない一方で、入力だけから攻撃成立を断定しない。必要な前提と迂回条件を確認する。
- 権限やリモート状態が必要な検証は、明示された許可の範囲に限る。確認できない部分はローカルの事実と推測に分けて報告する。
